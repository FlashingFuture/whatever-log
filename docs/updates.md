# 업데이트 전파 (새 버전 알림 → 한 번에 업데이트 → 배포 품질)

사용자가 새 버전을 알고 받을 수 있게 하는 구조다. 지금 번들은 **설치 프로그램 없이 zip을 푼 폴더**이고 **코드 서명이 없다**
(`docs/packaging.md`). 이 조건에서 위험이 낮은 것부터 세 단계로 간다.

| 단계 | 내용 | 상태 |
| --- | --- | --- |
| **1. 알림** | 새 버전이 있으면 화면 위에 알리고 릴리스 페이지로 안내한다. `whatever-log update --check` | **구현** |
| **2. 한 번에 업데이트** | 받기 → 서명·해시 검증 → 버전별 폴더에 풀기 → DB 백업 → 새 버전의 설치기 실행(넘겨받기) → 재시작 | 예정 |
| **3. 배포 품질** | 코드 서명(SmartScreen 경고 없애기), winget 등록 | 사용자가 늘면 |

## 다른 프로그램들의 방식과 우리가 고른 것

| 방식 | 예 | 우리 |
| --- | --- | --- |
| 알림만(확인 주소 하나, 받기는 사용자) | OBS, KeePass | 1단계 |
| 설치 파일을 받아 실행 | Notepad++(WinGUp) | 2단계의 "새 버전의 설치기 실행" |
| 버전별 폴더에 풀고 실행 지점만 전환, 이전 폴더 하나 보관 | Chrome, Squirrel(Discord·Slack), Velopack | 2단계의 폴더 구조. 지금의 "새 폴더에 풀고 `install.cmd`"가 이미 절반이다 |
| 스토어·패키지 관리자 | MSIX/Store, winget, Scoop | 3단계 |

공통 원칙(2단계에서 지킨다):

- **실행 중인 파일을 덮어쓰지 않는다.** Windows는 실행 중인 파일을 잠근다 — 새 위치에 풀고 전환한다.
- **받은 것은 검증한다.** 코드 서명이 없으니 확인 책임이 전부 우리 코드에 있다. 앱이 직접 받은 파일에는 브라우저의 "인터넷에서 받음" 표시(SmartScreen)가
  붙지 않으므로, 해시만이 아니라 **별도 서명 키로 서명한 매니페스트**를 확인한다.
- **업데이트를 적용하는 코드는 새 버전 쪽에 둔다.** 이전 버전은 받기·검증·새 설치기 실행만 하고, 교체는 새 버전의 `install`이 한다 — 업데이트 로직의
  버그를 다음 버전에서 고칠 수 있게.

## 1단계: 알림 (구현)

- **어디서 확인하나**: GitHub Releases API(`GET /repos/FlashingFuture/whatever-log/releases`). 따로 서버를 두지 않고, 이미 Release로 배포한다.
  로그인 없이 IP당 시간당 60회까지라 하루 한 번 확인에 충분하다. 요청에는 고정된 User-Agent(`whatever-log-update-check`)만 담는다.
- **언제**: 화면이 시작할 때 hub에 묻고, hub는 마지막 확인이 **24시간** 지났을 때만 GitHub에 묻는다(결과는 데이터 폴더의 `update-check.json`에 둔다).
  화면의 "지금 확인"이나 `whatever-log update --check`는 바로 묻는다.
- **무엇을 알리나**: 지금 버전보다 높은 가장 새 버전. 지금 쓰는 버전이 시험 버전(`-beta` 등)이면 시험 버전까지, 정식 버전이면 정식 버전만 알린다
  (SemVer 순서 — `1.0.0-beta.2` < `1.0.0-beta.10` < `1.0.0`). 초안(draft)과 태그 모양이 틀린 Release는 건너뛴다.
- **화면**: 상단 막대 아래 한 줄 — "새 버전 v1.0.0이 나왔어요(지금 v1.0.0-beta.2) · 받기 · 나중에 · 알림 끄기". "받기"는 릴리스 목록 페이지를 시스템
  브라우저로 연다(열 수 있는 바깥 주소는 hub의 고정 목록뿐이다). "나중에"는 **그 버전**만 다시 알리지 않는다(이 PC의 화면에 기억). "알림 끄기"는 확인 자체를 끈다.
- **개발 모양(저장소에서 `uv run`)에서는 확인하지 않는다** — 번들이 아니라 받아도 쓸 곳이 없다. `WHATEVER_LOG_UPDATE_CHECK=1`로 켤 수 있다(시험용).
- **강제 업데이트는 하지 않는다.** 서버와의 호환은 "이전 앱도 새 서버와 돈다"(docs/deploy.md 규칙 3)로 지킨다. 언젠가 호환을 깨야 하면 서버 `/version`에
  최소 앱 버전(`min_client`)을 두고 그보다 낮은 앱의 동기화만 막는다 — 자리만 남겨 둔다.
- **개인정보**: 확인할 때 GitHub가 이 PC의 IP와 User-Agent를 본다(로그인하지 않아도). 다른 값은 보내지 않는다. `docs/data-handling.md`에 적었고 화면에서
  끌 수 있다.

## 2단계: 한 번에 업데이트 (예정)

1. **받기**: 1단계가 찾은 Release의 zip 자산과 매니페스트(`release-manifest.json` + 서명 `.minisig`)를 받는다.
2. **검증**: 매니페스트의 서명을 앱에 넣어 둔 **공개키**로 확인하고(minisign/Ed25519), zip의 SHA-256이 매니페스트와 같은지 본다. 하나라도 틀리면 버린다.
   서명 키(비밀키)는 GitHub Actions의 비밀로만 두고 release 워크플로가 매니페스트에 서명한다. 키를 바꿀 때는 새 공개키를 담은 버전을 이전 키로 서명해 낸다.
3. **풀기**: `%LOCALAPPDATA%\whatever.log\app\<버전>\`에 푼다(버전별 폴더 — 실행 중인 이전 폴더는 건드리지 않는다). 사용자가 고른 폴더에 풀던 지금과 달리
   자리를 정해 둔다(Squirrel·Velopack 방식).
4. **DB 백업**: `recorder.db`·`goals.db`를 `backups\<이전 버전>\`에 복사한다. 마이그레이션은 앞으로만 가서(스키마 5인 `goals.db`를 이전 앱은 열지 못한다)
   되돌리려면 백업이 필요하다.
5. **넘겨받기**: 새 폴더의 `install`을 실행한다 — 지금도 하는 일(자동 시작·바로가기를 새 폴더로, 이전 폴더의 프로세스 끄기, 새 것 띄우기). 이전 버전 코드는
   여기까지 실행만 하고 끝낸다.
6. **정리·되돌리기**: 이전 버전 폴더 하나와 그 백업만 남기고 더 오래된 것은 지운다. 되돌리기는 이전 폴더의 `install` + 백업 복원.

## 3단계: 배포 품질 (사용자가 늘면)

- **코드 서명**: 서명하지 않은 exe는 처음 실행할 때 SmartScreen이 막는다. 오픈소스 무료 서명(SignPath 등)이나 클라우드 서명 서비스를 검토한다.
- **winget 등록**: 매니페스트를 올리면 `winget install`·`winget upgrade`로 받을 수 있다.

## 지금 나가 있는 버전

`1.0.0-beta.2`에는 알림 기능이 없다. 알림이 들어간 버전은 사용자가 **한 번은 직접** 설치해야 하고(`docs/packaging.md`의 업데이트 절차), 그 뒤부터
새 버전이 알려진다.
