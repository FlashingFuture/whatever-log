# Node.js / pnpm 버전 업그레이드 (2026-10)

## 배경

recorder의 틱 데이터를 일 단위로 집계하고 조회 UI를 붙이는 Phase 1~2 작업을 시작하기 전에,
지금 고정해둔 Node.js/pnpm 버전이 최신 보안 패치를 반영하고 있는지 점검했다. UI 프레임워크를
들이면 npm 의존성 트리가 지금(devDependency 4개)보다 훨씬 커지므로, 의존성이 적은 지금
버전을 올려두는 게 나중에 올리는 것보다 안전하고 쉽다.

## 발견한 문제

### pnpm 9.15.0 — EOL

`package.json`의 `packageManager`가 `pnpm@9.15.0`으로 고정되어 있었는데, **pnpm 9 라인은
2026-04-30부로 지원이 끝났다.** 이후로는 어떤 보안 패치도 받지 못한다.

현재 유지되는 라인(10.x/11.x/12.x)에서 최근 고쳐진 공급망 계열 취약점들:

- `CVE-2026-55698` (High, CVSS 8.8): 악의적인 저장소가 조작된 lockfile을 커밋해두면, pnpm이
  자동 버전 전환(automatic version switching) 중에 공격자가 지정한 코드를 실행할 수 있었다.
  10.34.2 / 11.5.3에서 패치.
- `CVE-2026-48995`: git 의존성의 tarball hash를 lockfile에 저장하지 않아서, 악의적인
  `codeload.github.com` 서버가 lockfile과 무관하게 임의의 tarball을 설치시킬 수 있었다.
  10.33.4 / 11.0.7 이전 버전에 해당.
- `CVE-2026-55487`: peer-suffix 정규화 결함으로, 승인된 소스 문자열 하나가 다른 소스를
  승인하는 것처럼 동작할 수 있었다. 10.34.2 / 11.5.3에서 패치.
- `CVE-2026-50573` (Medium): non-frozen 모드에서 무결성 검증에 실패한 tarball을 그대로
  받아들이고 lockfile을 갱신해버릴 수 있었다. 10.34.0 / 11.4.0에서 패치.

pnpm 9가 이 각각의 결함을 실제로 갖고 있는지는 개별 확인이 필요하지만, **EOL 라인이라는 사실
자체가 문제다** — 같은 종류의 결함이 발견되어도 더 이상 고쳐지지 않는다.

### Node.js — 2026-10-21 보안 릴리스 미반영

`.mise.toml`/`Dockerfile`이 `24.20.0`으로, `package.json`의 `engines.node`가
`>=22.22.1`로 고정되어 있었는데, **2026-10-21 Node.js 보안 릴리스**가 22.x/24.x/26.x
세 라인에 걸쳐 10개의 CVE를 패치하며 각각 22.23.4 / 24.22.1 / 26.12.1을 내놓았다. 주요
항목:

- Brotli 디코더의 out-of-bounds write (High, RCE 가능) — `fetch()`나 Express 5가 응답을
  자동으로 Brotli 압축 해제하는 경로에서 트리거하기 쉽다고 알려짐.
- TLS 인증서 호스트명 검증 우회, DNS 관련 SSRF 방어 우회 등 High 등급 이슈 다수.

고정해둔 `24.20.0`과 `>=22.22.1` 둘 다 이 패치 이전 버전이다.

## 결정

- pnpm: 현재 공식 `latest` 태그인 **12.15.0**으로 올린다. 10.x/11.x도 유지되고 있지만, 이미
  최신 안정 메이저가 나와 있는 상태에서 중간 메이저를 거쳐갈 이유가 없다 (의존성이 거의 없어
  마이그레이션 비용이 낮은 지금이 메이저를 건너뛰기 가장 좋은 시점).
- Node.js: `.mise.toml`/`Dockerfile`의 로컬 개발 버전을 **24.22.1**로, `engines.node`
  하한을 **>=22.23.4**로 올린다. 하한을 22.x 그대로 유지하는 이유는 — 이 값은 "Node 24
  기준으로 개발하지만 최소 이 버전까지는 동작을 보장한다"는 lint-staged의 실제 요구치이고,
  이번에 바뀌는 건 그 의미가 아니라 "그 하한선 자체가 취약한 패치 이전 버전을 가리키고
  있었다"는 것이기 때문이다.

## 앞으로

- UI 프레임워크를 고를 때 transitive 의존성 개수를 기준 중 하나로 삼는다 (Electron보다
  Tauri 같은 쪽이 JS 의존성 트리가 작아 공급망 노출이 적다).
- 런타임 의존성이 실제로 생기기 시작하면 pnpm의 `minimumReleaseAge` 같은 설정으로 방금
  올라온 패키지 버전의 설치를 일정 시간 지연시키는 걸 고려한다 (빠르게 퍼지는 웜성 공급망
  공격에 대한 완화책).
- 버전 고정값(Node/pnpm)은 "한 번 정하고 잊는" 값이 아니라, 의존성이 늘어나는 각 Phase
  전환점마다 다시 점검한다.
