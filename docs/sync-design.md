# 목표 동기화 설계 (로그인 사용자)

로그인하면 **목표(이름·하루 목표량·요일)** 를 서버에 두고, 여러 기기가 각자 **그날의 달성 시간** 을 서버로 보낸다.
**목표와 프로세스·사이트의 연결은 이 PC에만** 있고 서버로 가지 않는다. 로그인하지 않으면 지금처럼 모든 것이
로컬에서 돈다(`docs/auth-design.md`, `docs/data-handling.md`).

## 결정

| 주제 | 결정 | 이유 |
| --- | --- | --- |
| 서버가 아는 것 | 목표 이름, 하루 목표 시간, 요일, (기기·날짜·목표별) 달성 분 | 다기기 달성도와 보고서에 필요한 최소한 |
| 서버가 모르는 것 | 연결된 프로세스·사이트, 틱, 창·페이지 제목, URL, 시각 | 기존 약속 유지. 연결은 기기마다 다를 수 있다(모바일은 앱 이름이 다르다) |
| 목표 ID | 클라이언트가 만든 UUID v4 | 오프라인에서 만들고 나중에 올릴 수 있고, 기기 간 같은 목표를 가리킨다 |
| 달성도 저장 | **기기마다 따로 한 줄**(목표, 기기, 날짜) | 각 기기는 자기 줄만 쓰므로 동기화 충돌이 없다. 서버가 합산한다 |
| 합산 | 기기별 분의 합 | PC와 폰을 동시에 쓰면 겹쳐 세어질 수 있다(아래 한계) |
| 지난 날의 목표량 | 달성 줄에 그날의 목표량을 함께 둔다 | 목표를 나중에 바꿔도 지난 날 달성률이 바뀌지 않게(로컬 `GoalSnapshot`과 같은 원칙) |
| 목표 수정 충돌 | `revision` 낙관적 잠금. 다르면 409와 서버의 현재 값 | 두 기기가 동시에 고쳐도 한쪽이 조용히 덮어쓰이지 않는다 |
| 목표 삭제 | 삭제 표시만 남기고(이름은 지움) 그 목표의 달성 줄은 즉시 삭제. 30일 뒤 표시도 정리 | 다른 기기가 삭제를 알아야 한다. 데이터는 최소로 |
| 기기 ID | 기기가 처음 만든 무작위 UUID | 하드웨어 값(MAC, 시리얼, PC 이름)을 쓰지 않는다. 기기 삭제 API로 줄을 지울 수 있다 |

## 한계 (사용자에게도 알린다)

- 두 기기를 **같은 시간에** 쓰면 합산이 실제보다 커진다. "기기별 활성 시간의 합"이라는 정의 그대로다.
- 목표 **이름은 사용자가 쓴 글** 이다. "디스코드 1시간"처럼 쓰면 그 내용이 서버에 간다 — 이름 입력 화면에서 알린다.
- 서버는 날짜별 분만 안다(몇 시에 했는지, 어떤 앱인지는 모른다).
- 계정 삭제 API(`DELETE /account`)로 사용자 데이터를 모두 지울 수 있다.

## 클라이언트 (이 PC 쪽)

### 구성

| 부분 | 위치 | 하는 일 |
| --- | --- | --- |
| 서버 API 클라이언트 | `packages/cloud` (`cloud.api`) | 토큰을 달아 `/goals`·`/progress`를 부른다. 서버 응답 모양을 아는 곳은 여기뿐 |
| 동기화 로직 | `packages/goalsync` | 로컬 목표와 서버 목표를 맞춘다(계획 만들기·적용·주기 동기화·달성도 계산). 서버·로컬 DB 어디에도 직접 묶이지 않는 순수 로직 + 어댑터 |
| 동기화 에이전트 | `apps/sync` (`python -m sync_agent`) | hub와 **별개의 프로세스**. 일정 간격으로 `goalsync`를 돌린다. 화면·hub 없이 혼자 돈다 |
| 화면의 확인 창 | hub `/api/sync/*` + `apps/ui` | 로그인 직후 "어떤 목표를 서버에 올릴까요?"를 묻는다(아래) |

로컬 기능은 이 모든 것과 무관하게 돈다: `goals`·recorder·집계는 `cloud`·`goalsync`를 import하지 않는다(격리 테스트).

### `goals.db` 스키마 3 — 서버와의 연결 칸

`goals` 테이블에 칸을 더한다(기존 목표는 모두 `ask`로 올라온다).

| 칸 | 뜻 |
| --- | --- |
| `sync_state` | `ask`(아직 안 물음) / `sync`(서버와 동기화함) / `local_only`(사용자가 올리지 않기로 함) |
| `remote_id` | 서버의 목표 UUID. 비어 있으면 아직 서버에 없다 |
| `remote_revision` | 서버와 마지막으로 맞춘 `revision`(낙관적 잠금용) |
| `dirty` | 연결된 목표의 이름·목표 시간·요일을 로컬에서 고쳐 아직 서버에 못 보냄 |

별도 테이블: `sync_deletions`(로컬에서 지운 연결 목표의 서버 ID — 서버 삭제를 못 보냈을 때를 위해), `sync_meta`
(`sync_enabled`, 연결한 계정의 이메일). **프로세스·사이트 연결 테이블은 그대로이고 동기화와 아무 관계가 없다.**
프로세스 연결만 바꾸면 `dirty`가 켜지지 않는다(서버가 아는 칸이 아니므로).

### 로그인 직후: 기존 목표를 올릴지 정한다

로그인하면 화면이 hub에 "계획"을 묻고, 정할 것이 있으면 확인 창을 띄운다. 창은 **프로세스 등록 화면과 같은 체크 목록**이다
(목표를 새로 입력하는 폼이 아니다 — 이 순간에 필요한 것은 "넘길지 말지"뿐이라서). 서버에 이미 목표가 있을 수 있으므로(다른
기기에서 쓴 계정) 서버 목록과 함께 보여 준다.

| 항목 | 언제 | 체크하면 |
| --- | --- | --- |
| 서버에 추가 | 이 PC에만 있는 목표 | 이름·목표 시간·요일을 서버에 올리고 연결한다 |
| 서버의 목표와 합치기 | 이 PC와 **같은 이름**의 서버 목표가 있다(대소문자·유니코드 표현 무시) | 새로 올리지 않고 그 서버 목표와 연결한다. 목표 시간·요일은 **서버 값**으로 맞춘다(화면에 두 값을 함께 보여 준다). 이 PC의 프로세스 연결은 그대로다 |
| 이 PC에 추가 | 서버에만 있는 목표 | 연결이 비어 있는 목표로 가져온다(프로세스는 이 PC에서 직접 연결) |

- 기본 체크는 모두 켜져 있고, 체크를 끄면 그 목표는 `local_only`(올리지 않음)가 되어 다시 묻지 않는다. 화면의
  "목표 동기화" 버튼으로 언제든 다시 열 수 있다.
- **프로세스·사이트 연결은 어느 경우에도 올라가지 않는다.** 창에 그 사실을 적고, 올라가는 값(이름·목표 시간·요일)을 목표마다 보여 준다.
- 확인을 마치면 `sync_enabled`가 켜지고, 이후 새로 만드는 목표는 자동으로 `sync`가 된다(목표 만드는 화면에 "로그인 중에는
  이름·목표 시간이 서버에도 저장됩니다" 안내를 둔다).
- **계정이 바뀌면**(저장해 둔 이메일과 현재 로그인 이메일이 다르면) 이전 계정에 대한 연결을 모두 끊고(`remote_id` 비움,
  `ask`로 되돌림, `sync_deletions` 비움) 확인 창을 다시 연다. 다른 계정에 이전 계정의 목표가 올라가지 않게 한다.

### 에이전트가 주기마다 하는 일 (`sync_once`)

로그인되어 있고 `sync_enabled`일 때만 한다(아니면 아무것도 하지 않는다). 네트워크 실패는 다음 주기로 미루고, 기록·집계에는
영향이 없다.

1. **올리기(목표):** `sync` 상태이고 `remote_id`가 없는 목표 → `PUT /goals/{새 UUID}`(`base_revision: 0`). `dirty`인 연결 목표 →
   `PUT` + 현재 `remote_revision`. 응답이 409(다른 기기가 먼저 고침)이면 서버의 현재 revision 위에 **이 PC의 값을 다시 보낸다**
   (이 PC에서 방금 한 수정이 사용자 눈에 보이는 값이므로 되돌리지 않는다). 이름이 겹치면 연결하지 않고 `local_only`로 둔다.
2. **지우기:** `sync_deletions`의 서버 ID → `DELETE /goals/{id}`(이미 없어도 성공). 성공하면 지운다.
3. **내려받기:** `GET /goals`. `dirty`가 아닌 연결 목표는 서버 값(이름·목표 시간·요일)으로 맞춘다. 서버에서 삭제된 목표는 이 PC에서
   **지우지 않고 연결만 끊는다**(`local_only`) — 프로세스 연결이 사라지는 되돌릴 수 없는 일을 조용히 하지 않는다.
   서버에만 있는 목표는 여기서는 가져오지 않는다(가져오기는 사용자가 확인 창에서 고른다).
4. **올리기(달성도):** 연결된 목표마다 오늘과 지난 7일(처음 연결한 직후에는 30일)의 달성 분을 `recorder.db`에서 계산해
   `PUT /progress`로 보낸다. 마지막으로 보낸 값과 같은 줄은 보내지 않는다(`sync.db`에 기록). 요일에 적용되지 않는 날은
   달성 분이 0이면 보내지 않는다.

에이전트 자신의 상태(기기 ID, 마지막으로 보낸 값)는 `apps/sync/sync.db`에 둔다. 기기 ID는 처음 실행할 때 만든 무작위 UUID다.
`goals.db`는 hub와 에이전트가 함께 쓴다(WAL 모드, 쓰기는 `BEGIN IMMEDIATE`로 직렬화 — 기존 설계 그대로).

### Docker: 서버(Cloudflare 쪽)를 로컬에서 똑같이 띄운다

에이전트를 실제 Cloudflare에 올리지 않고도 끝까지 시험하려고, 서버(Worker + D1)를 컨테이너에서 띄운다
(`docker compose up server`). `wrangler dev`가 D1 대신 로컬 SQLite를 쓰고, 그 파일은 이름 붙은 볼륨에 남는다.

- 마이그레이션은 컨테이너가 시작할 때 자동으로 적용한다(`wrangler d1 migrations apply DB --local`).
- Google 로그인은 비밀 키와 브라우저가 필요하므로 시험에서는 쓰지 않는다. 대신 **개발 전용 스크립트**가 로컬 D1에 시험용 사용자와
  토큰을 직접 넣고 토큰을 출력한다(`--remote`는 거부한다). **서버 코드에는 인증을 건너뛰는 길을 만들지 않는다.**
- 에이전트는 `WHATEVER_LOG_SERVER_URL=http://127.0.0.1:8790`과 `--token-from-env`(환경 변수 `WHATEVER_LOG_TOKEN`)로 그 서버를
  가리킨다. 환경 변수 토큰은 읽기 전용 저장소로만 쓰이고, 운영 경로(자격 증명 관리자)는 바뀌지 않는다.
- 통합 시험(`apps/sync/tests/test_e2e_server.py`)은 이 서버가 떠 있을 때만 돈다(기본으로는 건너뜀).
- recorder는 Windows 화면을 읽으므로 컨테이너에서 돌지 않는다. 컨테이너에는 서버만 있다.

## 서버 API (`apps/server`)

모두 `Authorization: Bearer <토큰>`이 필요하다(없거나 만료면 401). 응답은 `Cache-Control: no-store`.

| 요청 | 설명 |
| --- | --- |
| `GET /goals` | 내 목표 전부(삭제 표시 포함). 목표는 최대 20개라 페이지가 없다 |
| `PUT /goals/{id}` | 목표 만들기·수정. `{name, daily_target_minutes, weekdays, base_revision}`. 새 목표는 `base_revision: 0`, 수정은 현재 revision. 같은 내용으로 처음 만드는 요청을 다시 보내도 200(재시도 안전). revision 불일치·삭제된 목표·이름 중복·20개 초과는 409 |
| `DELETE /goals/{id}` | 목표 삭제(그 목표의 달성 줄도 삭제). 이미 삭제됐으면 204 |
| `PUT /progress` | `{device_id, entries: [{goal_id, day, minutes, target_minutes}]}` 최대 50개를 이 기기의 줄로 덮어쓴다. 없는(삭제된) 목표는 `ignored_goal_ids`로 돌려준다. 기기는 사용자당 10대까지 |
| `GET /progress?from=&to=` | 날짜 구간(최대 400일)의 목표·날짜별 합산: `{goal_id, day, minutes, target_minutes, percent, devices}` |
| `DELETE /devices/{device_id}` | 그 기기가 보낸 달성 줄을 모두 삭제 |
| `POST /auth/logout` | 이 토큰을 서버에서 폐기(204) |
| `DELETE /account` | 사용자와 목표·달성·토큰을 모두 삭제(204). 되돌릴 수 없다 |

## 비용 (Cloudflare 무료 한도 기준, 도입 전 요금 페이지 재확인)

- 사용자 1명이 1년 동안 쌓는 달성 줄은 (목표 5개 × 기기 2대 × 365일) ≈ 3,650행으로 작다.
- 요청마다 D1 읽기 1~2회(토큰 확인). 동기화는 변경이 있을 때만 하고 한 번에 50줄을 묶어 보내 쓰기 횟수를 줄인다.
- 아직 없는 것: 요청 속도 제한. 사용자가 늘면 Cloudflare 규칙으로 로그인·쓰기 경로를 제한한다.
