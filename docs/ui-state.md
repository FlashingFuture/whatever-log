# 화면(UI)의 상태 관리 전략

`apps/ui`는 프레임워크 없이 TypeScript로 DOM을 직접 그린다. 상태를 어디에 두고 어떻게 바꾸는지 정해 두지 않으면
같은 값이 여러 곳에 복사되어 어긋나기 쉬우므로, 상태의 종류별로 자리를 정한다. 로그인 상태가 이 전략을 처음
적용한 사례다.

## 상태는 네 종류로 나눈다

| 종류 | 예 | 어디에 두나 | 이유 |
| --- | --- | --- | --- |
| 서버(hub) 데이터 | 사용량, 목표, 로그인 여부 | **hub가 진실**. 화면은 받아 온 값을 잠깐 들고 있는 사본 | 화면을 닫았다 열어도 같아야 한다. 화면이 따로 저장하면 hub와 어긋난다 |
| 주소(어느 화면) | 홈 ↔ 프로세스 상세 | URL 해시(`router/`) | 새로고침·뒤로 가기가 그대로 동작한다 |
| 앱 전체가 같이 보는 화면 상태 | 로그인 상태 | `state/`의 저장소(store) | 상단 막대, 서버 기능 등 여러 곳이 같은 값을 봐야 한다 |
| 한 컴포넌트 안의 일시적 상태 | 팝업이 열렸는지, 입력 중인 값, 펼친 목록 | 그 컴포넌트의 클로저 | 다른 곳이 알 필요가 없다 |

**브라우저 저장소(`localStorage`, `sessionStorage`)는 쓰지 않는다.** 로그인 토큰은 물론 로그인 여부도 저장하지
않는다. 앱을 다시 열면 hub에 다시 묻는다 — 저장해 둔 사본이 실제와 어긋나 "로그인된 줄 알았는데 아니었다"가 되는
일을 없애려는 것이다(토큰은 이 PC의 자격 증명 관리자에만 있고 화면에는 오지 않는다, `docs/auth-design.md`).

새 상태를 만들 때는 위 표에서 가장 위(바깥)에 둘 수 있는 곳에 둔다. 컴포넌트 안에서 충분하면 저장소를 만들지
않는다 — 저장소는 두 곳 이상이 같은 값을 봐야 할 때만 만든다.

## 저장소(`state/`)의 규칙

1. **단계(phase)는 이름 붙은 몇 개뿐이다.** 여러 불리언(`isLoading`, `isLoggedIn`, `hasError`…)을 조합해
   추측하지 않고, 가능한 단계를 한 타입으로 닫아 둔다. 불가능한 조합(로그인됐는데 로그인 중)이 타입으로 생기지
   않는다.
2. **어떤 단계에서 어떤 단계로 가는지는 순수 함수 `reduce(상태, 이벤트)` 한 곳에 있다.** DOM·네트워크를 모르므로
   그대로 단위 테스트한다. hub의 응답을 단계로 옮기는 규칙(`snapshot` → 단계)도 여기에만 있다.
3. **화면은 단계만 보고 그린다.** 컴포넌트는 저장소를 구독해 그리기만 하고, 로그인 규칙은 모른다. 사용자의 동작은
   저장소의 함수(`login`, `logout`, `cancelLogin`)로만 넘긴다.
4. **hub와 주고받는 통로는 주입한다.** 저장소는 실제 `fetch`가 아니라 `AccountApi` 인터페이스를 받는다. 테스트는
   가짜를 넣고 시계도 직접 움직인다.
5. **오래된 응답이 새 상태를 덮지 못하게 한다.** 요청마다 번호를 매기고, 가장 최근 요청의 응답만 반영한다
   (로그인 중 조회 응답이 로그아웃 응답보다 늦게 오는 경우 등). 거꾸로 **변경 요청(로그인·취소·로그아웃)이 오가는 동안에는 조회를 보내지
   않고** 끝난 뒤 한 번 보낸다 — 변경이 끝나기 전에 보낸 조회가 변경 전 상태를 읽고도 "더 최근 요청"이 되어 변경의 응답을 밀어내면, 다시 묻는 타이머가 없어
   화면이 틀린 채로 남는다.
6. **층 규칙:** `state/`는 `api`와 `lib`만 가져온다(`tests/architecture.test.ts`). 화면(`components`,
   `layouts`, `pages`)을 가져오면 테스트가 실패한다. 화면이 `state/`를 가져오는 것은 허용된다.

## 로그인 상태

### 단계

| 단계 | 뜻 | 화면 |
| --- | --- | --- |
| `loading` | 처음 hub에 묻는 중 | 아무것도 그리지 않음(깜빡임 방지) |
| `signedOut` | 로그인 안 됨. 직전 로그인 시도가 실패했다면 사유(`error`)가 있다 | "로그인" 버튼 |
| `signingIn` | 시스템 브라우저에서 로그인하는 중 | "로그인 중…" 버튼, 팝업에 안내와 "취소" |
| `signedIn` | 로그인됨 | 이메일과 "로그아웃" |
| `unavailable` | 로그인 기능을 쓸 수 없다. `reason`이 `hub`(연결 안 됨)인지 `cloud`(이 설치에 기능 없음)인지 구분한다 | 비활성 "로그인" 버튼, 이유는 툴팁 |

```
loading ──조회 성공──▶ signedOut ──로그인 시작──▶ signingIn ──성공──▶ signedIn
   │                      ▲  ▲                        │  │                │
   │                      │  └────실패·취소────────────┘  │                │
   │                      └──────────────로그아웃──────────┼────────────────┘
   └──조회 실패──▶ unavailable(hub) ──5초마다 재조회──▶ (조회 성공 시 위 단계로)
```

`unavailable(cloud)`는 재조회하지 않는다(이 설치에서는 바뀔 일이 없다).

### 흐름

1. **시작:** `main.ts`가 저장소를 하나 만들고 `refresh()`로 hub에 묻는다. 창으로 돌아올 때(`focus`)도 다시 묻는다.
2. **로그인:** 로그인 방식 버튼(hub가 준 `providers` 목록으로 그린다) → `POST /api/account/login` → hub가 시스템
   브라우저를 열고 스레드에서 로그인을 진행한다 → 화면은 `signingIn`이 되어 **1초마다** `GET /api/account`로 결과를
   묻는다 → `signedIn`(또는 실패 사유와 함께 `signedOut`)이 되면 묻기를 멈추고 팝업을 닫는다.
3. **취소:** `DELETE /api/account/login`. hub의 로그인 스레드가 곧 끝나면서 단계가 돌아온다(응답이 아직 진행 중이라고
   해도 폴링이 이어져 결국 따라간다).
4. **로그아웃:** `POST /api/account/logout`. hub가 서버의 토큰 폐기를 시도하고 이 PC의 로그인 정보를 지운다. 지우지
   못하면 로그인 상태를 유지한 채 오류 문장만 보여 준다(로그아웃된 것처럼 보이면 안 된다).
5. **hub 연결 끊김:** 조회가 실패하면 `unavailable(hub)`가 되고 **5초마다** 다시 묻는다. hub가 늦게 뜨거나 재시작해도
   화면이 스스로 돌아온다.

### 오류 문장

- hub가 사유를 준 오류(`ApiError`)는 그 문장을 보여 준다(모두 사용자용 한국어 문장이다).
- 연결 실패 같은 나머지는 우리가 정한 문장("로그인을 시작하지 못했습니다.")을 보여 준다 — `Failed to fetch` 같은 영어
  예외 문구를 화면에 내지 않는다.
- 이미 진행 중이라는 `409`는 실패가 아니라 "화면이 낡았다"는 뜻이라서, 오류를 띄우지 않고 상태를 다시 물어 맞춘다.

### 확장: 로그인 방식을 늘릴 때

화면은 하드코딩된 버튼이 아니라 hub가 준 `providers`(`{id, label}`)로 버튼을 그린다. 새 방식(예: Kakao)을 붙일 때
화면이나 저장소는 바꾸지 않는다.

1. `packages/cloud`의 `PROVIDERS`에 `Provider`를 한 줄 추가한다(`cloud/providers.py`).
2. 서버(`apps/server`)에 그 방식의 코드 교환 주소(`/auth/<id>`)를 추가한다.
3. 버튼 글자는 "`<이름>` 계정으로 계속하기"로 자동으로 만들어진다.

## 동기화 확인 창의 상태

"목표 동기화" 확인 창(`components/sync/SyncDialog.ts`)은 위 표의 **네 번째 종류**(한 컴포넌트 안의 일시적 상태)다. 두 곳 이상이 같은
값을 봐야 하지 않으므로 저장소를 만들지 않고 창의 클로저에 둔다: 불러온 계획, 체크한 항목(`selection`), 처리 중(`busy`), 결과, 오류.

- **계획은 창을 열 때마다 hub에서 새로 받는다**(저장해 두지 않는다 — 서버·이 PC의 목표가 그 사이 바뀌었을 수 있다). 가장 최근
  요청의 응답만 반영한다(창을 연달아 열어도 낡은 응답이 덮지 않는다).
- **순수 규칙은 `lib/syncBoard.ts`에 있다**: 기본 선택(전에 "올리지 않기"를 고른 목표는 꺼 둠), 항목 옮기기, 설명 문장, 요약. DOM·hub를
  모르므로 그대로 단위 테스트한다(`tests/lib/syncBoard.test.ts`).
- **언제 자동으로 여나**: `main.ts`가 계정 저장소를 구독하고, 로그인 시도 감시자(`createLoginWatcher`)가 "사용자가 로그인을 시도해서 로그인됨이 된 순간"에만 `open({afterLogin: true})`를 부른다. 시도는 `signingIn`뿐 아니라 요청이 오가는 동안(`signedOut` + `busy`)도 세므로, 로그인이 시작 응답보다 먼저 끝나 `signingIn`을 거치지 않아도 열린다. 앱을 열 때 이미 로그인된 경우나 창으로 돌아와 다시 조회한 경우는 열지 않는다.
  이 계정에서 이미 확인했거나 정할 것이 없거나 서버에 닿지 못하면 조용히 넘어간다(로그인은 성공했고, 버튼으로 나중에 열 수 있다).
- **적용 중에 창을 닫았다 다시 열면** 새 계획을 받지 않고 진행 중인 화면을 그대로 보여 준다(새로 받으면 적용 버튼이 되살아나 같은 선택을 두 번 보내거나, 먼저 보낸 적용의 결과가 새 계획을 덮을 수 있다).
  적용 요청에는 계획을 받은 계정(`email`)을 함께 보낸다.
- 적용 결과에 따라 이 PC의 목표가 바뀌면(합치기·가져오기) 현재 화면을 다시 그린다. 409(로그인 필요)를 받으면 계정 상태를 다시 묻는다.

## 동기화 상태 칩·기기 관리·계정 삭제의 상태

세 가지 모두 **한 컴포넌트 안의 일시적 상태**(표의 네 번째 종류)라 저장소를 만들지 않았다:

- **상태 칩**(`SyncStatusChip`): 칩은 `<button>`이라 키보드로 포커스해 자세한 안내(팝업)를 열 수 있다. 마지막으로 읽은 상태와 타이머를 클로저에 둔다. 로그인한 동안만 주기적으로 묻고(`setActive`), 요청마다 번호를 매겨 낡은 응답을 버린다. 칩에 무엇을 쓸지·언제 다시 물을지는
  순수 함수(`lib/syncStatus.ts`)다. 상태를 읽지 못해도 오류를 띄우지 않고 직전 값을 유지한다. 로그인 상태(계정 저장소)는 칩을 켜고 끄는 신호로만 쓴다.
- **기기 관리**(`DevicesDialog`): 열 때마다 목록을 새로 받는다(저장해 두지 않는다. 다만 지우는 중이면 새로 받지 않는다). 목록을 받은 로그인(`email`·`session`)을 들고 있다가 지우기 요청에 되돌려 보낸다. 지우는 중에 창을 닫았다 다시 열었다면 그동안 계정이 바뀌었을 수 있어서, 지우기가 끝난 뒤 목록을 새로 받는다. 확인을 열면 "취소"에, 취소하면 "지우기"에 포커스를 둔다(창 안의 버튼이 교체돼도 포커스가 제목으로 빠지지 않게). 지우기 확인 중인 기기, 처리 중, 오류만 창 안에 둔다. 정렬·이름·지울 수 있는지는 `lib/devices.ts`.
- **계정 삭제**(`DeleteAccountDialog`): 체크·입력한 이메일·처리 중·결과를 창 안에 둔다. 체크박스는 교체하지 않고(포커스를 잃지 않게) 삭제 버튼 상태만 바꾼다. 삭제 중이거나 결과를 아직 안 봤다면 다시 열어도 초기화하지 않는다. 삭제 버튼이 눌리는 조건과 삭제 뒤 문장은 `lib/deleteAccount.ts`. 이메일 입력 칸은 다시 그리면 커서를 잃으므로
  입력할 때는 버튼 상태만 갱신한다. 서버에서 지워졌을 때(또는 응답을 못 받아 처리됐을 수 있을 때)는 계정 저장소에 다시 묻게 한다(`onDeleted`·`onSignedOut`). 계정 저장소는 로그인 세션 키(`session`)와 삭제 불확실 표시(`deletionUncertain`)도 들고 있고, 계정 메뉴는 다시 읽은 뒤에도 **세션이 그대로면 열어 둔다**(삭제가 실패했을 때 메뉴가 닫혀 재시도 길이 사라지지 않게). 팝업은 자기를 연 버튼의 것만 닫는다(`closePopoverFor`): 상태 칩이 숨겨질 때 계정 메뉴를 닫지 않는다.
- 동기화를 켰거나 적용하면 `main.ts`가 계정 저장소와 상태 칩을 함께 다시 읽게 한다.
